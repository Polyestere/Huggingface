# 젠토 인턴십 프로젝트 일지

## 프로젝트 개요

FastAPI를 활용한 AI 기반 이미지 및 영상 생성 서비스 테스트용 개발

## 📅 일별 진행 상황

### 1일차 - 환경 구성 및 기초 학습

**주요 작업**

- 개발 환경 구성
    - PyTorch, CUDA, Anaconda, VSCode, Python 설치
- FastAPI 사용법 숙지
- **HuggingFace 모델 활용 학습**
    - Text-to-Video: Wan2.1
    - 번역: NLLB, opus-mt-ko-en
- 이미지 생성 API 구현
    - 번역 모델: opus-mt-ko-en
    - 이미지 생성: SD v1.5, v3.5M

**어려웠던 점 및 느낀 점**

학교에서 진행했었던 프로젝트들과 다르게 처음부터 환경 구성을 진행해야했음.
허깅페이스와 모델 사용에 대한 경험 미숙으로 제대로 갈피를 잡지 못함.
FasAPI 같은 사용자의 요청에 따라 상호작용하는 서버의 작동방식에 대한 이해도가 부족했음.


### 2일차 - 모델 최적화 및 품질 향상

**주요 작업**

- 이미지 및 영상 생성 최적화
- **다양한 번역 모델 테스트**
    - opus-mt-ko-en
    - opus-mt-big-ko-en
    - NLLB_distilled_600, 1.3B
- **생성 모델 활용**
    - SD v3.5M
    - WAN2.1 1.3B
- 프롬프트별 이미지 생성 테스트
- 모델 파라미터 조절

**어려웠던 점 및 느낀 점**

FastAPI의 get, post 메소드 등의 기초적인 활용만 필요했던 탓에 사용법 숙지가 어렵지는 않았음.
AI로 이미지, 동영상을 생성하며 GPU 성능이 왜 중요하다고 하는 지 알 수 있었음.
전체적인(VRAM 및 RAM) 메모리 관리의 중요성을 깨달을 수 있었음.
인공지능에게 얼마나 세부하게 프롬프트를 주느냐에 따른 결과물과 소요시간 차이를 파악하고, 프롬프트 엔지니어링의 중요성을 다시 깨닫는 계기가 됨.       

### 3일차 - 동시 요청 처리 구현

**주요 작업**

- **병렬 처리 시스템 구현**
- 다중 모델 선택 기능 추가
- 동시 요청 처리 속도 개선

**해결 방안 모색**

- 번역 모델을 CPU에 로드하여 GPU 부하 감소
- VRAM 사용량 모니터링 및 동적 모델 로딩
- 동일 모델 재사용 최적화

**어려웠던 점 및 느낀 점**

아침에 갑작스럽게 동시 요청 처리가 필요하다는 요구사항이 들어와 모델별 순차 처리로 만들던 것을 병렬처리로 구현할 필요성이 생김.
병렬 처리를 구현 시에 여러 혹은 동일 모델을 동시에 로드해야 하기 때문에 메모리 부족을 해결할 필요가 있었음. 
이를 해결하기 위해 번역 모델을 cpu에 로드해 gpu 부하를 줄임
이미지 생성 모델은 파라미터 조절 및 모델 별 사용 VRAM 규정을 통해 현재 사용 중인 VRAM에 여유 공간이 있으면 Load 아니면 대기하다가 Load 방식으로 구현. 
만약 Load 시에 요청 사항과 동일 모델이 이미 Load 되어있다면 Load 해제하지 않고 그대로 사용하게끔 함. 
하지만 Load 시에 속도가 느려 Postman의 Performance 테스트 시에 1분을 초과해 ESOCKETTIMEOUT 에러가 발생함.

### 4일차 - 성능 테스트 및 개선

**주요 작업**

- Postman을 활용한 동시 요청 테스트
- GET 요청으로 사용 가능한 모델 정보 제공
- 파이프라인 풀 구현
    - 각 모델별 2개씩 파이프라인 생성
    - 모델별 병렬 처리 최적화

**성과**

- SD 1.5 모델 성능 개선
- SD 3.5M 모델은 여전히 메모리 이슈 존재

**어려웠던 점 및 느낀점**

여전히 병렬처리를 위해 필요한 여러 요소들을 확보하기 위해 방안을 탐색함. 
사용자가 여러 모델을 선택할 수 있게끔 하는 기능 추가 필요성이 생김.
동시요청을 위해서는 병렬처리가 필요한데 이는 동시요청의 빠른 처리를 위해서임. 
병렬 처리는 많은 메모리를 요구하고 만약 이미 파이프라인에 로드되어 있는 것과 다른 모델을 로드하게 되면 교체 시간 때문에 처리 시간이 늦어지는 상황이 발생함.
이를 위해 파이프라인 풀을 현재 하드웨어에 맞게 각 모델 별 두개를 생성해놓고 요구 시마다 각 모델별 병렬처리가 이루어지도록 개선함.
SD_1.5 모델은 해결되었지만 여전히 SD_3.5M 모델은 메모리 소모가 커 생성이 느림.    

### 5일차 - 성능 벤치마킹

**주요 작업**

- 대규모 동시 요청 테스트
- 성능 병목 지점 분석 및 해결

**테스트 결과**

- **Stable Diffusion 1.5**
    - 3개 요청, 3명 가상 사용자, 2분 테스트: 35초 이하 생성, 타임아웃 없음
    - 5개 요청부터 타임아웃 발생
- **Stable Diffusion 3.5M** 지속적인 개선 중

**해결 방안 모색**

- 시퀀스 다이어그램 분석을 통한 병목 지점 파악
- 이미지 생성 후 경로 반환 순서 최적화

**어려웠던 점 및 느낀점**
SD_1.5의 Performance 테스트 시 3명까지는 에러가 없지만 4명부터 Timeout 에러가 발생. 
현재 코드의 시퀀스 다이어그램을 통해 문제점을 파악함.
이미지 생성 직후 경로를 반환하지 않고 모델의 파이프를 반환 후 경로를 반환해 시간 소요가 발생. 
순서를 바꿔 문제를 해결함. 
여전히 5명 이상부터 에러가 발생해 이는 하드웨어 부족으로 판단함.

### 6일차 - 영상 생성 및 웹 UI 구현

**주요 작업**

- 영상 생성 기능 추가
    - Wan2.1_1.3B 모델 적용
- 웹 UI 구현 및 테스트
- 모델 로드 시간 최적화
- 파라미터 조절을 통한 생성 시간 단축

**프로젝트 방향 변경**

- 병렬 처리 → 순차 처리로 변경
- 결과물 품질보다 생성 속도 우선
- 상업용 라이센스 사용 가능

**어려웠던 점 및 느낀점**

현재 프로젝트는 테스트를 위한 프로그램을 만드는 것이기 때문에 산출 결과물 보다는 속도가 중요하다고 함. 
상업용 라이센스를 신경쓸 필요가 없어져 모델 선택의 자유도가 늘어남.
병렬처리가 아닌 순차처리로의 변경과 비디오 생성 모델의 추가, 웹 페이지의 구현이 필요해짐.
GPT, Perplexity, Claude 등 AI의 활용으로 보다 높은 퀄리티의 프로젝트 수행이 가능해졌지만 그 만큼 소프트웨어의 이해와 흐름 및 구조 파악의 중요성이 증가했다는 생각이 들었음. 
                 
### 7일차 - 영상 생성 최적화

**주요 작업**

- 웹 UI 기능 개선
- 영상 생성 파라미터 최적화
- 새로운 모델 탐색
    - CogVideoX-2b 모델 테스트

**해결 방안 모색**

- 생성 속도와 품질의 균형점 탐색
- 영상 생성에 집중한 개발 방향 설정

**어려웠던 점 및 느낀점**

순차처리로 구조가 변경되었으므로 이미지보다는 영상 생성에 집중하기로 함. 
테스트 용이므로 결과물의 완성도보다는 생성 속도가 중요했으므로 파라미터를 조정해 빠르게 나오면서도 적절한 완성도를 보이는 균형점을 찾기로함. 
Wan2.1_1.3B 모델 조정 후에는 다른 적용할만한 모델을 찾음.

### 8일차 - 코드 모듈화 및 리팩토링

**주요 작업**

- 코드 모듈화 진행
- 새로운 영상 생성 모델 테스트
    - LTX 0.9.6 모델 평가
- 성능 저하 원인 분석

**문제점 파악**

- 모듈화 과정에서 기존 코드와의 충돌 발생
- Wan2.1_1.3B 모델 성능 저하 원인 분석 필요
  
**어려웠던 점 및 느낀점**
코드의 모듈화 과정을 진행하고 나니 기존 웹 페이지와 다른 코드 등에 충돌이 생겨 디버깅 과정이 필요했음. 
Wan2.1_1.3B 모델의 이미지 추론 및 생성 속도가 현저하게 느려져 원인을 찾아야만 했음


### 9일차 - 프로젝트 완료 및 문서화

**주요 작업**

- 최종 코드 완성
- 요구사항 문서 작성 (마크다운 형식)
- 모듈화 코드 오류 해결
- Wan2.1_1.3B 성능 저하 원인 해결
    - `pipe.enable_model_cpu_offload()` 코드 누락이 원인
    - `pipe.to("cuda")` 사용 시 GPU 공유메모리 과다 사용으로 속도 저하


**어려웠던 점 및 느낀점**
전체적인 코드에 대해서 모듈화를 하면서 필요없다고 생각했던 코드가 의외로 속도, 결과물 등 여러 요소에 영향을 준 것들이 많았음.
다시 한 번 AI의 무지성적인 사용보다는 코드의 흐름과 의미 파악이 중요하다는 생각이들었음.

## 🎯 핵심 

1. **하드웨어 리소스 관리의 중요성**
    - GPU, RAM, VRAM 최적화
    - 모델별 메모리 사용량 분석
2. **프롬프트 엔지니어링**
    - 세부적인 프롬프트의 결과물 품질 영향
    - 생성 시간과 품질의 트레이드오프 관계 파악
3. **시스템 아키텍처 설계**
    - 병렬 vs 순차 처리 선택
    - 병렬 처리 시의 메모리 관리
    - 실시간 성능 모니터링
4. **코드 품질 관리**
    - 모듈화의 중요성
    - 작은 변경사항의 큰 영향
